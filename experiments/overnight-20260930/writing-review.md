# 執筆・日記・別窓の独立レビュー

対象: v0.5.0 / `426e477`。2026-09-30。既存IABとユーザーのブラウザデータへ触れず、専用の一時Chromeプロファイルで確認した。共有`src`と既存テストは変更していない。

結論: 今夜の次の一歩は、**文章を失わずに書き続けられること**。新しい常駐方式やOS入力取得より、下書き保持、別窓同期の抜け、同日保存の競合対策が毎日の試用につながる。

## 今回追加した再現

`node experiments/overnight-20260930/review-writing.mjs`（Chromeとlocalhost:4173の起動済み試作が必要）。結果は `review-output/writing-results.json`。これは不具合の観測用スクリプトで、成功条件を定義した回帰テストではない。採用修正後は結果が変わる。

| 再現 | 観測 | 重要度 |
| --- | --- | --- |
| `?write`を2タブ開き、各々で異なる1行を渡す | 先のタブの`一人目の文章`はメモリに残るが、同日保存は後のタブの`二人目の文章`だけへ置換される | 高: 日記の上書き |
| `?write`と`?companion`を開き、執筆側の「ことば」から`表面 黄色 立方体`を送る | 執筆側449文字/cube、別窓1文字/condense | 中: 下部の操作を使うと横の存在が反応しない |
| 執筆で一行取り込み→別窓同期→HELPから「最初へ」 | 本体1文字、別窓7文字のまま | 中: 同じ日が別の形になる |
| 履歴キーに壊れたJSONを入れ、新しい一行を送信 | 現在の文字は描画されるが、以後の保存が失敗する。壊れたデータは保持される | 低: 復旧口がなくなる |
| 先頭が空行の原稿で、先頭位置からEnter | 他行を誤って追加しない | 問題なし |

## 修正提案の順序

### 1. 未送信の文章を再読込で失わない

現状は画面に明示した仕様どおり、下書きを保存しない（`companion.ts:14,84–106`）。したがって不具合とは区別するが、日常の執筆を横で支える仮説には最も価値がある追加。

- 原稿全体とカーソル位置を、日記の形とは別の小さな保存領域へ置く。入力の短い待ち時間後とページ非表示時に保存。未送信の文章を自動で形へ送らない。
- 日付が変わっても書きかけの原稿を消さない。形の日付と原稿の寿命を分ける。
- 「原稿を消す」と「形を最初へ」を分ける。形の実験で文章が消える経路を作らない。
- 保存エラー時には執筆を止めず、原稿のテキスト書き出しができるようにする。日記JSONのみでは未送信の行を救えない。
- 2タブ競合対策なしに同じキーへ下書きを保存すると、新しいデータ消失経路になるため次項と合わせる。

最小の確認: 途中まで入力→再読込→同じ原稿/同じカーソル、未送信行は0回追加。日付替わりと保存エラー後でも原稿保持。

### 2. 同日保存の無言の上書きを止める

`writeDay()`は同日分を置換する（`diary.ts:46–48`）。各writerは起動時にだけ今日を復元し（`companion.ts:81`）、他writerの更新を取り込まない。`BroadcastChannel`も一つの固定名なので複数writerの形・下書きが同じviewerへ届く。

今夜は共同編集を実装する必要はない。**一つの執筆タブを編集元に限定し、二つ目は読むだけにする**か、保存世代の変化を検出して上書きを止め、現在の原稿を書き出せるようにする。単なる保存直前の比較だけでは同時書き込みを完全には防げない点は残る。状態の自動合成は取り込み済み行の二重追加につながるため安易に行わない。

最小の確認: 2タブを開いてそれぞれ入力しても、先の保存文を黙って消さない。二つ目のタブを閉じる時の`pagehide`にも注意（この経路も現状は保存する）。

### 3. 形の変更を一つの通知口へ集める

執筆欄の`feed()`は`publish(); save();`を呼ぶが、通常ターミナルの`addText()`、HELPの4形状ボタン、リセットは通知しない。クイック形状だけが`publish()`を呼ぶ（`main.ts:109–135,171–187`）。

描画状態が変わった時に呼ぶ共通処理へ、別窓通知と必要な保存を集約する。描画フレームごとの通知ではなく、文字追加・形選択・リセット単位にする。日記を眺めるだけの復元を今日の保存へ書き戻さない。

最小の確認: 執筆欄、ターミナル、形状ボタン、リセットで本体と別窓の`count/spec`一致。別窓を後から開いても最新状態。同期後のアニメーション位相まで完全一致させる必要は今回ない。

## 現在うまく守られている点

- 書くモードの取り込みは1倍。通常ターミナルの初期64倍とは異なる。32,000は描画粒子の上限で、通常の執筆なら一日あたりおよそ32,000個の非空白書記素まで。別に1,024種類、1行の入力はUTF-16長16,384まで。
- 上限を超えた行は執筆欄へ残る。部分的に入った場合、日記のbatchには全文と実際の追加数が記録される。ただし後半が描画されたわけではない。保存成功メッセージだけではこの差が分かりにくい。
- 日付替わりは前日保存に成功してからresetする。保存容量エラー時に前日の文字を消さない。
- アーカイブ閲覧は`beforeArchive`へ今日を退避し、戻る時に復元する。日記表示中は通常操作がinert。今日への保存と過去日の閲覧が混ざらないようにしている。
- 別窓は`ready`に対する最新スナップショットを受けるので、開いた時点の復元がある。
- 配列やshape等を検証し、無効なJSONをそのまま日記として採用しない。

## 次へ回してよいこと

- 32,000上限そのものを増やす。まず上限とは別に全文を保存できると、将来は描画だけ間引く方法へ移行できる。
- 任意アプリのキーログ、OS常駐、毎朝の自動起動。今回の価値検証に不可欠ではない。
- 14日分のクラウド同期。ローカルの書き出し/読み戻しを先にする。
- 日記のJSON読み戻しは現状未実装。追加するなら一時的な`Matter`で全batchを復元検証し、成功後に現在の状態へ反映する。現状`restoreDay()`は途中で文字数不一致になると対象Matterをresetするため、インポートで直接呼ぶと作業中の形を失う。
- 壊れた保存の復旧では、生データの書き出し口を残し、勝手に壊れた履歴を消さない。

## 確認の限界

今回の実操作はChromeの一時プロファイルによるローカルUI操作と開発用inspectの比較。実OSのIME、Document PiPの最前面表示、Windows、Safari、実際の一日分の執筆や14日経過を試したものではない。日付替わりと容量エラーの既存テストはソースを確認し、本レビューでは重複実行していない。

## 採用した修正（同日の後続作業）

レビュー後、rootから独立実装を依頼され、以下を反映した。コミット・公開はrootの統合時に行う。

- 原稿全文と選択位置を、日記とは別のキーへ400msの待ち時間後に保存。ページ非表示/移動時にも保存。未送信行は再読込後も自動投入しない。日付替わり、形のリセットで原稿を消さない。原稿のテキスト書き出しを追加。
- Web Locksで執筆元を1タブに限定。二つ目は読み取りで開き、元を閉じて「ここで続きを書く」で同じ原稿/今日の形を引き継ぐ。ロック非対応ブラウザは執筆を読み取りとし、その理由を表示。一般のアート画面は遊べ、明示的な保存時だけ同じロックを短く取得する。
- 通常ターミナル、2種類の形ボタン、リセットの変更も別窓へ送信し、writerでは保存。保存失敗と同期通知を分離。各変更前に日付替わりの保存が成功したかを確認し、深夜0時直後の入力を前日に混入させない。
- 日記/原稿の保存が壊れている場合は無言で置換せず、「壊れた保存を退避して再開」から復旧。元の生データを別キーへ退避できた時だけ置換し、原本のダウンロードも行う。退避用の容量まで不足する場合は、現在の原稿/日記を書き出せる。
- 日記の復元は一時的なMatterへ全batchを検証してから反映。不一致で現在の形を失わない。

変更ファイル: `src/companion.ts`, `src/diary.ts`, `src/main.ts` の連携部、`src/diary.test.ts`, 新規`tests/writing-reliability.spec.ts`。styleは変更しなかった。

確認: 既存ブラウザ19件＋追加の最初の7件をまとめて成功。その後、破損原稿/0時直後の通常入力を追加し、追加9件すべて成功。最後のロジック検証はrootの並行追加分を含む36件成功、型確認とビルド成功。ブラウザの実IME/Windows/Document PiPは未確認のまま。

今回の新しい限界: 原稿の保存長はUTF-16で1,000,000まで。それを超えた場合は保存エラーの表示とテキスト書き出しに留め、入力自体を切り捨てない。読み戻せる日記JSONファイルのインポートは未追加。旧v0.5.0のページを同時に開き続けている場合、その旧コードはWeb Locksに参加しないため、ロックの保護対象は今回の版を読み込んだページ間に限る。
