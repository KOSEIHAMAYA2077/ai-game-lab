# 計算領域を縮める資源診断 R1

Bonsai 1.7B / 4B の計算領域を縮めて、形選択の結果、応答時間、サーバーのメモリを比較した。**メモリは下がったが、現条件でも軽いウィジェットとしての常駐量は大きい。** 4Bを返信後に10分待機させるとCPU負荷は低かったが、約1.28 GiBのサーバーRSSを保持した。

これは先の形選択比較で既に用いた36文の再実行で、資源設定による退行を調べる開発診断である。未見文での能力や一般化、モデル自体の改善を示す試験ではない。ケース・prompt・scorerを変更していない。

## 設定と意味の確認

| 設定 | 基準 | 縮小版 |
| --- | ---: | ---: |
| context tokens | 2048 | 1024 |
| batch | 256 | 64 |
| ubatch | 128 | 32 |
| max output tokens | 256 | 128 |

CPU 4スレッド、threads-batch 4、temperature 0、seed 17、prompt cache off、GPU offを共通にした。同じモデルファイル・runtime binary・prompt・fixtureのSHAを照合。保存されたHTTP要求36本ずつは `max_tokens` 以外同一、CLIは context / batch / ubatch とポート以外同一だった。期待値・説明・分類groupをモデルへ送っていない。

| 候補 | 完全一致 / 36 | 契約適合 / 36 | 変形要求 / 24 | 保留 / 12 | 保留文への誤提案 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Bonsai 1.7B Q1 基準 → 縮小 | 16 → 16 | 36 → 36 | 16 → 16 | 0 → 0 | 12 → 12 |
| Bonsai 4B Q1 基準 → 縮小 | 28 → 29 | 35 → 36 | 20 → 21 | 8 → 8 | 4 → 4 |

1.7Bは正解から不正解への変化0件、不正解から正解への変化0件。外見から蛇を指定した `appearance12` の誤答先だけ fish → jellyfish に変わった。4Bは `mixed06` の契約違反が、正しい snake 提案へ変わった1件のみ。正解を失ったケースはない。縮小した4条件を同時に変え、各1回だけ試したため、1件の差を特定の設定変更の効果に帰属しない。

全ケースで `action` と有限12形の `shape` だけを厳密採点した。任意の3Dメッシュ生成や色・個数・動き抽出の精度を示すものではない。保留すべき文への誤提案は残っており、この結果だけで普段の入力から無確認に変形する既定モデルには採用しない。

## メモリと応答

| 候補 | サーバーRSS最大 MiB 基準 → 縮小 | 応答中央値 秒 基準 → 縮小 | 縮小版の応答最大 秒 | 縮小版の起動 秒 |
| --- | ---: | ---: | ---: | ---: |
| Bonsai 1.7B Q1 | 819.3 → 697.8 | 1.005 → 1.070 | 1.166 | 0.593 |
| Bonsai 4B Q1 | 1496.4 → 1336.1 | 2.450 → 2.640 | 2.864 | 1.021 |

両候補とも36返信を完了し、timeout / runtime failure はなく、所有プロセスの終了を確認した（exit code 0）。モデルファイルの量は変わらず、1.7Bは236.8 MiB、4Bは545.8 MiB。ダウンロード量と常駐RAMは別に扱う。

RSSはサーバー単独の250ms間隔の標本最大で、瞬間ピークを逃す可能性がある。4Bの縮小版は待機600秒を含む長い計測窓だが、待機開始前の起動・36返信の区間で採った最大も1336.1 MiBだった。1.7Bは短い実行全体の最大である。UI・入力監視・計測処理・OSのRSSやGPUメモリを合計した値ではない。

応答はHTTP要求から全文返信までで、純decodeの速度、入力から画面上の形が完成する時間とは異なる。起動前にファイル全体をhashしたため、起動は管理したコールドキャッシュ測定ではない。速度は1回ずつの観測値で、反復して統計的に優劣を確認していない。

既に提案された一時512 MiBのウィジェット枠と比べ、今回の最小サーバーRSS最大はなお697.8 MiBだった。全体資源、実16GB laptop、他作業との共存、電力・温度は未確認である。

## 4Bを読み込んだまま600秒待機

| 指標 | 検算済み観測値 |
| --- | ---: |
| 実経過 | 600.074476542 秒 |
| サーバーCPU時間の増分 | 0.75 秒 |
| CPU増分 / 実経過 × 100 | 0.12498448598%（1コア = 100%） |
| 待機RSS min / max / mean | 1313.1875 MiB（すべて同値） |
| 待機RSS有効標本 | 2268 |

CPUは `ps TIME` の累積 user + system 時間を開始・終了で読み、差を実経過で割った。ローカルmacOSの `man 1 ps` で定義を確認した。子プロセスの終了CPUを合算する `-S` は使っていない。マルチスレッドで複数コアを同時使用すれば100%を超えうる定義であり、マシン全体の占有率ではない。

タイマーは開始counterの読み取り前から終了counterの読み取り後までなので、`lsof` / `ps` の小さな実行時間を分母に含む。TIME表示の精度にも限界がある。計算率と増分、待機RSSのmin/max/meanと標本数を、保存されたsummaryと生標本から独立に再計算して一致を確認した。`status=completed` だけで600秒の成立を判断せず、実経過を確認した。

この待機は「36回推論した後、モデルを保持し、入力を送らない状態」を1回だけ測ったもの。1.7Bの待機、モデル終了後の基準、起動・推論時CPU、描画や入力監視込みのCPU、電力・温度・2時間の成長は測っていない。低い待機CPUから、アプリ全体の軽さや電池への影響を結論しない。

次は、文字の表示・成長をモデルと切り離し、意味解釈が必要な時だけ起動して終了する構成を評価する。常駐CPUと常駐RAMを分け、入力の頻度、再起動を含めた待ち時間、他作業との共存を実利用に近い環境で測る。約698 MiB以上の処理中のピークと誤提案の課題は、終了する設計だけでは解決しない。
