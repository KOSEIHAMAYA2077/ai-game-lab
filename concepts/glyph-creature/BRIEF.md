# 文字を食べる存在 - 最初の試作案

2026-09-30。ユーザー回答は確定事項として記録し、ここで追加した具体的ルールは提案として分ける。仮称は整理のためのもの。

## 一文の遊び

**中央の「@」に日本語・英字・記号を自由に食べさせると、その文字が体に残り、姿と反応が変わっていく。よく分からない存在を、自分の入力で育てながら観察する。**

> 真ん中に＠マークだけが初めある．
> ＠や「あ」[a][?]などを入力していく（ターミナルのようなものが下にある）ことで形が変わっていく．
> 食べさせていった文字による変化を楽しむ．

> そのうち異形のようになっていく．あるいは人型を形成する，あるいは途中で要求してくる．みたいな．
> 添付の画像のようなイメージたち．

原案の「＠」をASCIIの「@」へ固定するかは未確定。実装時は開始記号を一つにし、入力された両者は別の見た目として保持する提案。

## 画像から何を使うか

5点の原画像はローカルに保存し、公開版には[観察内容](references/README.md)を残した。以下の「採り入れる」は提案であり、画像をそのままゲーム素材へ使うという意味ではない。

| 画像 | 観察できる特徴 | 今回への読み替え |
| --- | --- | --- |
| 1・2 | 「あ」の大きな形や、細かい要素の集合でできた形 | 同じ文字の増減だけでなく、集合の組み方で身体が変わる |
| 3 | 文字で構成された幾何形、流れ、人型、異形 | 文字を身体の材料として見せる。全ての形や3D描画を初回の要件にしない |
| 4 | 中心、周囲の粒、重なった軌道・層 | @の周囲に文字が集まり、まとまりを作る配置の参考 |
| 5 | 黒背景、文字・記号、罫線、簡潔な情報表示 | 画面の雰囲気の参考。ダンジョン探索を追加する根拠にしない |

文字が体を作る部分は、このアイデアを試すために必要。普通のモンスター画像の段階切替だけでは代用しない。一方で、完璧な人型の輪郭、CRT効果、凝ったウィンドウ装飾は初回には不要。

## 今回の試作で確かめたいこと

H1: 同じ量でも異なる文字を与えると違う姿や反応になり、次に別の文字を試したくなる。

H2: 少数の反応でも「この存在を観察していたい」「自分の育てたものだ」と感じる余地が生まれる。

H1は形の分岐が機能するかをAIも確認できる。H2の愛着は本人の試遊で判断する。AIの自己採点をユーザーの感想と扱わない。

## P0として提案する体験

最初は黒い観察領域の中央に記号が一つある。下に入力欄があり、日本語・英字・記号を好きに入力して送る。送るとその文字が周囲に現れ、身体の一部になる。次に別の文字を与えると、既存の文字も含めて配置が変わり、まとまりや輪郭が変化する。

存在は毎回説明文を返すのではなく、給餌の時に少しこちらへ寄る、同じ文字を続けるとまとまり方や反応が変わる、手を止めると短くこちらをうかがう、といった少数の反応を見せる。これらは実装候補であり、全て必須ではない。正体や「正しい餌」は説明し切らず、入力と変化のつながりは観察できるようにする。

```text
┌─────────────────────────────────┐
│                                 │
│          観察する領域           │
│                @                │
│                                 │
├─────────────────────────────────┤
│ > 文字を入力して与える           │
└─────────────────────────────────┘
```

これは情報配置の概念図。ターミナル風は見た目と操作の参考で、本物のコマンド実行は不要。初回からコードエディタ、ファイルツリー、大量のパネルを再現しない。

## 最小範囲の提案

| 入れる | 理由 |
| --- | --- |
| 日本語・英字・記号の自由入力、送信 | プレイヤーの試行そのもの |
| 食べた文字が見える身体 | 与えたものと結果を結ぶ |
| 少なくとも2方向の異なる形への変化 | 単なる文字数増加以上の発見を試す |
| 給餌時と観察中の少数の反応 | 存在への関心や愛着を試す |
| 最初からやり直す操作 | 別の文字列を比較する |
| 開発用の再現・状態確認 | AIが変更の結果を自分で確かめる |

初回は触り始めて数分で複数の変化が分かる密度を目指す。これは試遊の目安であり、5分で強制終了する仕様や、製品のクリア時間ではない。勝敗やエンディングを無理に追加しない。

ユーザーが保留したもの: 成長による自動化。

AIが初回の範囲から外すことを提案するもの: 放置報酬、通貨、ショップ、威力やレベルの最適化、転生、進化図鑑、要求クエスト、物語の完結、人型への確定した到達経路、複数生物の管理、オンライン機能、長期保存。インクリメンタル全体を今後も採用しないという決定ではない。

人型・異形・要求イベントは元のアイデアとして残す。P0で核が成立してから、興味が向いた部分を次の試作に選ぶ。

## 変形ルールの実装案 - 承認後に調整する細部

最初はルールベースで試す。入力された字形を保持しつつ、文字の種類や繰り返しの割合など少数の特徴から、密度、まとまり、広がり、曲がり方を変える。個々の文字を2Dの位置へ並べ、全体の形を作る。

例として、同じ開始状態から「aaaaaa」「ああああああ」「??????」を与え、同じ量でも少なくとも二つが違うまとまりに育つようにする。具体的にどの文字が丸くなる、枝になる、といった対応は仮調整であり、ユーザーが決定したものではない。

無作為な形へ毎回変わるだけにしない。入力の痕跡を保ち、同じ開始状態・同じ入力・同じ経過時間で再現できるようにする。全Unicode文字へ固有の進化規則を作る必要はない。通常の日本語・英字・記号を受け付け、表示できない文字や長すぎる入力は壊れずに扱う。

このP0では、言葉の意味を理解して自由会話する外部LLMを必須にしない。開発にAIを使うことと、ゲーム動作に生成AIを組み込むことは別の選択。語義に応じた反応が核になった場合に改めて設計する。

## 技術・素材の提案

- Vite + TypeScript + Canvas 2D、通常のHTML入力欄。Canvasに日本語入力機構を独自実装しない。
- UIの少量の文字と罫線はHTML/CSS、身体はCanvas。文字は自由配置し、全て同幅のRogue格子へ押し込まない。
- 日本語対応フォント一種を採用。Noto等の既存フォントを使い、独自フォント・モデルは作らない。初期実装時に必要な利用条件を同梱する。
- 音は核の判断に必要なら既存の短い音を使う。初回の完成条件にBGMや音の磨き込みを入れない。
- 現状は3D、Phaser、PixiJSを必須にしない。文字描画が実測で支障になるまで変更しない。

## AIが実際に確かめること

1. 初期画面の中心に種となる記号が一つあり、入力へ進める。
2. 通常の入力欄から「a」「あ」「?」を与え、送信ごとに一度だけ状態が変わる。
3. 食べた文字が身体に見えて残る。文字列ログだけが増える状態ではない。
4. 同じ量の異なる入力列で、単なる大きさ以外の配置・輪郭の差が出る。
5. 反応が実際の給餌・観察の状態と結び付いている。
6. リセット後、同じ入力列・同じ時間の進め方で結果を再現できる。
7. 空入力、貼り付け、長い入力、混在した文字でも操作不能にならない。
8. 日本語の変換確定で誤送信せず、確定後の送信で一度だけ食べる。実IME未確認なら未確認と記録する。

コードだけでなく、通常入力を経由した画面と状態で確認する。Macでの確認をWindowsの確認済みとは扱わない。細かな見た目のピクセル一致を合格条件にしない。
