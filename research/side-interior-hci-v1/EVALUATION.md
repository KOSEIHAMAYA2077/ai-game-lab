# 表示・注意・資源を分けた評価案

これは未実施のプロトコル候補。既存の[明示要求の研究プロトコル](../widget-study-protocol-v1/README.md)に対する別資料で、既存の開発・未見評価を変更しない。

この案で確かめたいのは、入力の痕跡を保つ表示が、本人の選んだ時に見返せるものとして仕事の横に置けるか、という判断である。内容解釈の正解率、作業の成績、見返したい気持ち、資源予算の合格を一つの点数へ足さない。

## 何を測ったかを区別する

| 領域 | 指標と単位 | 分かること・分からないこと |
|---|---|---|
| 主課題 | 固定課題の正答/エラー数、完了秒、途中の停止回数 | 生産性の一部。自由創作の品質・本職の生産性とは別 |
| 中断 | widgetを見て主課題を止めたepisode数/露出時間、戻るまで秒。刺激発生と時刻を照合 | 直後の停止だけではwidgetが原因とは言えない。本人の事後説明、観察分類、原因不明を別に残す |
| 視線 | 装置がある将来試験はwidget AOIへのfixation回数・dwell秒・onsetとの関係 | 視線と注意は同じではない。クリックや自己報告をeye trackingの実測にしない |
| 装置なしの観察 | 同意した短期試遊のみ、widget方向を見る/主課題継続/止まるを符号化。二人で一部を独立分類 | 粗い視方向の観察。周辺注意を証明しない。曖昧コードと一致率を示す |
| 本人の報告 | 邪魔1〜7、好み1〜7、見返したい1〜7、理由、不要だった時間。任意の非使用も記述 | この案独自の項目で、検証済み尺度とは呼ばない |
| workload | 必要なら正式NASA-TLXの指示・採点に従う。加重/非加重を先に固定して明記 | 主観負担。短い独自質問をNASA-TLXと命名しない。[NASA公式](https://www.nasa.gov/human-systems-integration-division/nasa-task-load-index-tlx/) |
| 動作 | 文字取りこぼし/重複、保存成功、queue、表示遅延ms、frame時間ms、形変更回数 | 文字の完全性・描画品質。快適性の代用品ではない |
| 資源 | process tree CPU%、RSS/footprint MiB、GPU時間、ディスク、wakeups、電力Wまたは電池Wh | 単位・対象を揃えて比較する。モデルファイルの小ささと窓全体RAMは異なる |

CPUが低くても明るい動きは妨げ得る。頻繁な注視は好奇心にも強制的な捕捉にもなり、少ない注視は安心にも無関心にもなり得る。見た回数の大小だけを成功へ読み替えない。専門点検の先行と、観察・面接の組合せは文献S3/S4を参考にするが、われわれの人数や秒数は独自の候補。[出典表](LITERATURE.md)

## 段階1：人を呼ぶ前の工学試験と専門点検

同じ人工確定入力と同じseedで、本文/形/色/文字IDを固定したreplayを作る。100/1,000/4,000文字burst、長い静止、連続変更候補を含める。OS全体入力収集を前提にしない。IME・取得元の適法性やcommit品質は別担当の入力契約で確認する。

既定の6 Program、別の60形確認、保存状態、視認できる文字面を通過した候補だけを進める。3〜5人の専門点検を行う場合は、遮蔽、映像の気付き方、過不足、対応の一貫性、止める/隠す自由、エラー時の表示を個別に挙げる。点検者と後述の6人試遊者を母数に足し合わせない。

## 段階2：6人の短期試遊は探索として行う

対象は、PC上で文書・創作・プログラミングのどれかを日常的に行う成人6人を将来募る案。今回募集・連絡・実施はしていない。6人から普遍的な快適性、非劣性、統計的検出力を主張しない。

最初の約50分は、以下の一つの比較だけに絞る。タスク内容はモデルの未見例文ではなく、独立に作成した固定作業を使い、試遊で露出した意味解釈例は将来の未見評価から外す。

| 時間 | 内容 |
|---|---|
| 5分 | 用途・収集項目・隠す/終了の操作説明。私的本文は不要 |
| 5分 | 専用欄で練習。素材として蓄積する入力と明示命令を区別 |
| 3×8分 | Off / 文字面の静止 / 同じ文字面の穏やかな動き。全6順序を一人ずつに割当。各条件に同難度の文書修正・短いコード追跡・配置編集の課題セットを用意 |
| 各条件後2分、計6分 | 邪魔・見返したい・好み、どの瞬間が中断になったか。誘導せず理由を聞く |
| 10分 | 自由に隠す/戻す試行と面接。作業の跡として何を感じたか、変化に意味を求めたか |

静止/動きは文字数、カメラ、形、窓寸法・位置を揃える。Offは非表示だが裏の人工入力/保存条件を揃える。Offまで含む資源試験では表示コストと保存コストを分離する。この短期比較はまず表示の妨げを扱い、人工replayを使った結果から本人の実入力の痕跡が価値を持ったとは主張しない。本人の入力との因果感・見返す理由は専用欄の自由試行と自宅試用で別に尋ねる。

O=Off、S=静止、M=動き。A/B/Cはそれぞれ文書修正・コード追跡・配置編集を含む等価セットとする。下表を登録前の割当候補として凍結し、募集後に参加者を行へ無作為割当する。各表示条件が各セットを2回ずつ、各periodも各表示/各セットを2回ずつ持つ。課題難度は本試遊とは別の事前確認で合わせ、条件を知った後の課題・採点変更をしない。

| 割当行 | period1 | period2 | period3 |
|---|---|---|---|
| 1 | O / A | S / B | M / C |
| 2 | O / A | M / C | S / B |
| 3 | S / C | O / B | M / A |
| 4 | S / C | M / A | O / B |
| 5 | M / B | O / C | S / A |
| 6 | M / B | S / A | O / C |

個人差と三課題の差を図示し、条件別の実数・中央値・ばらつき、具体的失敗episodeを報告する。平均の好みだけで採用しない。仮にp>.05でも「作業に影響なし」としない。将来の確認試験で非劣性を主張するなら、許容する成績低下幅、対象母集団、必要情報量、検出力を別に事前設定する。

### 配置と反応頻度は次の別セッション

短期試遊の50分へ全要因を詰め込まない。配置はP0/P1/P2の品質通過条件を、同じ固定表示で各8分、全6順序で比べる。隠せる/背景条件は別に露出率と再表示の手間を観察する。透過も別比較とし、形品質を下げて成績だけ良く見せない。

反応頻度は、同じ文章列・同じ候補形列で、固定periodic / 安定窓に応じた低頻度 / 本人の任意変更を比べる。総変化量を揃えた表示スケジュール試験を先に行う。任意変更には自己選択があり、同じ刺激実験の順位とは解釈しない。内容器の評価は別に凍結し、ambient文を命令用positive/hold正解へそのまま採点しない。

## 段階3：数日の自宅試用は慣れの入口を観察する

6人・5作業日の探索案。初日baseline/導入、残る4日をA2日+B2日とし、AB/BAを3人ずつに割当。Aは文字蓄積のみ、Bは同じ蓄積＋固定した安定窓/低頻度の内容反映候補。配置・fps・色・保存量を固定する。短期からBのモデルや保持秒数を選んだ場合、これは開発版の探索であり未見の確認試験ではない。

一日の通常作業の横で最大8時間観察できる設計だが、8時間の作業を被験者へ強制しない。実際の使用時間・可視時間・入力があった時間を別に記録する。会議・休憩・fullscreen・機密作業では本人が休止できる。Bは未実装の将来条件なので、入力契約と品質が通るまでホーム試用を開始しない。

毎日2分の終業日誌、途中と最終に各15分面接を提案する。日誌は「見返した/戻した/隠した/不要だった/意味が分からなかった/作業の跡に感じた」時点を短く尋ね、本文引用を要求しない。初日の新鮮さと後日の関わりを分ける。最終日に、戻しやすさ、続けたい/持ち帰りたくない理由を聞く。

5日では習慣形成・長期愛着・生産性改善は確認できない。日・課題・入力量・持ち越した文字の履歴を記録して、効果と混同しない。A/Bの履歴は別々のローカル状態から同量で始め、期間内は累積する。実験全体での痕跡が断ち切られる影響は限界として記載する。自然な連続蓄積は、その後の数週間の任意観察で別に調べる候補に残す。定着を強制しない。非使用・削除・配置変更も結果であり、欠測の理由を記録する。

### 収集の最小範囲

OS全体の取得は今回開始していない。将来試用も、本人が許可した取得元と確定品質を明示する。自宅の画面/視線/生本文を研究側へ常時収集する設計にしない。既定の研究ログは件数、時刻、同意した形ラベル、queue/遅延、隠す/再開、資源集計とする。本文が必要な追加評価は別途本人が選んだ人工例または研究用文章を使う。研究ログの公開時に本文が混ざっていないか確認する。外部モデルへ入力を送らない。

## 8時間の資源・安定性試験

これは人の8時間の注意評価とは別。工学試験では、人工replayで入力の累積と静止を制御する。

| 項目 | 比較設計 |
|---|---|
| 実機 | 一般的な16GB PCを一台以上、最終対象のmacOS/Windowsを別々に記録。OS、CPU/GPU、解像度、倍率、電源、他アプリを固定して報告 |
| 条件 | Off / static / 10fps / 15fps、同一文字数・形・入力。各30分窓、最初5分はwarmupとして別記。順序を変えて各3回 |
| 8時間 | 選んだ固定候補を正常ウィンドウで連続動作。周期的burst→静止、予定した形変更、隠す/再開を含む。30分集計と時間別の傾向を保存 |
| 資源 | renderer/main/helperを含むprocess tree、CPUを1論理コア=100%に換算、RSS/footprint、GPU/IO、wakeups。既存モデル表のbyte数とは別 |
| 暫定予算 | CPU時間平均≤5%の1論理コア、process tree RSS≤200MiBをまず試す候補。OS footprint等も併記。文献の標準や達成値ではない |
| 電力 | 同一電源・画面輝度でOffとの差を測る。実測W/Whか、OSの推定・Energy Impactかを明記。Energy ImpactをWへ換算しない。[Apple公式](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/MonitoringEnergyUsage.html) |
| 故障 | crash、入力欠落/重複、保存失敗、無制限queue、退避後の勝手な再表示、定常容量後のRAM増加、形の崩れを個別件数で保存 |

入力累積中の正当なメモリ増加と、上限到達後の増加を分ける。固定文字数の静止区間を設け、warmup後の傾向と入力総量を同じ図に載せる。各processのRSS合計は共有ページの二重計上があり得るので、実物理RAMの占有量とは呼ばず、process別値とOS footprintも併記する。安定と称するには全予定のreplay・最終ID/色/状態hashが一致し、各故障件数と資源傾向を確認する。

現在のMacがロックされたoffscreen試験は、正常な可視窓・常時最前面・他の作業アプリとの競合を含む測定ではない。現在のsoakの結果や進行をこの資料で更新・合算しない。8時間の工学安定も、8時間作業して快適だったという証拠にはしない。

## 失敗・保留・未判定の報告

| 分類 | 扱い |
|---|---|
| 明示要求の誤採用 | 知らない形、否定、引用、競合などから形を動かす。positive:hold比率を固定して示す。accepted precision、coverage、hold false activationを層別報告 |
| ambientの意味違い | 変更理由が本人の作業感覚と一致しない。主観評価と候補/保持/変更logを対応させる。「正解形」を事後に作らない |
| 正しい保留 | 不確かな内容で既定の形を保つ。無変化を一律失敗にしない |
| 表示品質失敗 | 面の崩れ、読めない文字、色の喪失。遮蔽やCPUが改善しても合格にしない |
| 注意上の失敗 | 本人が意図せず主課題を止めた、退避した、作業が悪化した。原因不明を別区分にし、気に入ったという報告で相殺しない |
| 未判定 | n=6、短期、欠測、装置なし、課題差、confidence intervalが広いなど。差なし/快適/長期定着へ変換しない |

未見モデル評価は開発・表示校正とは独立に凍結する。既存fresh120/fresh140を見た後の変更は次版の回帰であり、同じ評価を未見と再命名しない。将来の人間評価の文章が解釈器の開発へ入った場合、exact文だけでなく同じsource-document / paraphrase / template group全体を確認用未見から除く。このgroup境界をtrain/dev/heldout分割前に固定し、同義語置換や同じ作業文書の派生例を独立未見と称さない。60形、6 Program、人数、episode数の分母を毎回明記する。

明示要求の評価では、次の母数を事前に固定する。曖昧例は独立層にし、exact shapeと許された近接familyも別に採点する。

| 指標 | 分母 |
|---|---|
| positive coverage | 採用した明確要求数 / 明確要求の全数 |
| accepted-positive exact precision | 正しいexact形を採用した明確要求数 / 採用した明確要求数。保留層の誤発火を含まない条件付き指標と明記 |
| 明確層joint accepted precision | 正しいexact形を採用した明確要求数 / （採用した明確要求数＋採用してしまった明確hold数）。曖昧層は分母に含めない。positive:hold構成比を必ず併記 |
| hold false activation | 採用してしまった明確hold数 / 明確holdの全数 |
| raw top1 exact / near family | 閾値保留前の正解数 / 明確要求の全数。familyをexactへ足さない |

各件数と割合を一緒に出し、positiveに条件付けた100%だけで実使用の誤作動がないとはしない。現実の要求率が未知なら、人工fixtureの構成比を実使用率と称さず、明示モードの率の感度分析を別に示す。ambient本文はそもそも命令ではないので、命令分類のpositive/hold比率を全入力へそのまま移さない。

独立読取レビューでは、表示条件と課題セットの交絡、文単位だけの除外による派生例の漏れ、joint指標の曖昧層の扱いが指摘された。上の割当表・group分離・分母注へ反映済み。レビュー担当は資料を読むだけで、app・モデル・fixtureを編集していない。
