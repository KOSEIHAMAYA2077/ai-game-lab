# 常駐する文字の身体を、ウィジェット程度の負荷にする

2026-10-02。ユーザーの追加条件を受けた設計更新。以前の16GB PC向け研究、既存コード、保存tag、公開版は残す。この文書は次の別版の設計で、軽量化が完成したという報告ではない。

## ユーザーが確定した条件

別の作業の横で動かす用途に合わせ、メモリやCPUを使い切らず、ウィジェット程度の負荷を目指す。16GBに収まるだけでは合格にしない。文字が身体の表面を流れ、自由な文章が材料になる表現は保つ。既存物は削除しない。

この条件を、以前の[全アプリ6GiBという研究用候補](16gb-text-to-3d-20261002.md#8-次の版へ進む条件)より優先する。約30秒までの生成演出は許容されていても、常時重い計算を続ける許可とは扱わない。

## 今のコードで先に改善するところ

- `program-main.ts` のframeは停止・非表示でも `scene.render(0)` を呼ぶ。`scene.ts` のrenderは文字ごとの位置・姿勢を計算し、バッファと画面を更新する。時間の停止と処理の停止を分ける。
- `scaffold-model-client.ts` は一度準備したWorkerとモデルを正常時も保持する。常駐する表示と、文章を解釈する処理の寿命を分ける。
- 既存sceneはアンチエイリアス、描画バッファ保持、最大2倍の画素比を使う。小窓の実寸に合わせて画素数を制限し、通常の動きを15〜20fps程度で比較する。

ソースの確認元は[保存した0.13.1](https://github.com/KOSEIHAMAYA2077/glyph-matter/tree/glyph-matter-v0.13.1-twist.1/prototypes/glyph-creature/src)。これはコード読取レビューで、常駐RAMの実測ではない。

## 次の別版の構成案

**常駐するのは文字の身体と軽い動き。文章の意味を形に変換する処理は入力時だけ。**

1. 表示中は緩やかな流れと変形を低い更新頻度で続ける。吸収中だけ頻度を上げる。非表示・停止時は描画要求そのものを止め、再表示・入力・視点操作で必要な分だけ再開する。
2. 形を変更する必要がある入力にだけ予測器を使う。同じ内容や対応済みの指定は保存した結果も使う。全文書を毎フレーム解析しない。入力本文を外部へ送らない。
3. 解釈後に残すのは短い形状Programと文字・入力色。大きいWorkerは終了し、描画だけを続ける。中断中の古い返答を採用しない。終了によってRAMが実際に戻るかも測る。
4. 蓄積した文章の保存量と、同時に描く文字数を分ける。画面に合う文字数を選び、面の被覆を保つ字の大きさ・配置を比較する。見た目を疎らにしただけで軽量化成功としない。元の文章と色の履歴を捨てない。
5. 本格的な常駐ウィンドウ化は、以上の負荷を小窓で測った後に判断する。OS全体の入力監視や設定変更はこの設計に追加しない。

## 数値は、まず試すためのAI提案

以下は達成済みの値ではない。約400×400の小窓、他アプリで執筆中を最初の条件とする。対象16GB laptop CPU/iGPUの実測が必要で、このMacの値で代用しない。

| 状態・項目 | 最初の候補目標 |
| --- | --- |
| 停止・非表示 | 文字位置の更新・描画0回。アプリ由来CPUはほぼ0 |
| 通常の穏やかな動き | 15〜20fps、平均CPUは1論理コア換算で5%以内 |
| 描画処理 | 1回のCPU処理時間p95が3ms以内 |
| 通常時の全体RAM | 200MiB程度以下 |
| 文章解釈中のRAM | 短時間ピーク512MiB以内。超える方式は常駐版への採用を見送る |
| 蓄積 | 30分・2時間で使用量が増え続けず、入力の保存成功を確認 |

低fpsでも各フレームが重ければCPUを占有するため、更新頻度と一回の計算量の両方を見る。GPU負荷・電力も記録し、CPUだけが低いことを合格にしない。

初回の約128MBは公式モデルとtokenizerの取得ファイル量。ブラウザの実RAMではない。取得バッファ、展開・推論セッション、作業領域、文字atlas、GPU資源、ブラウザの関連プロセスもある。現版の常駐総RAMは未測定。

共有ブラウザでは入力前後の増分と、その計測に含まれるプロセスを記録する。将来の専用ウィンドウでは関連プロセスとGPU分を含む測定方法を定義する。RSSの単純な合計で共有メモリを二重計上しない。ディスクのモデルcache、JS heap、プロセスの実メモリを分けて報告する。

## 学習研究の位置づけ

研究・教師データ生成は制作時に行い、利用中の常駐予測器には小さい役割を持たせる。以前の[文字片の線形分類器](../experiments/word-shape/README.md)は配布JSON773,901 bytesで、候補の比較基準になる。ただし対応は当時の10形と見送りで、複合部位や否定を自由に理解できるモデルではない。ファイルサイズだけで実RAM・意味精度を評価しない。

次は限定した構造・局所属性を予測する小さい分類器/回帰器を比較し、必要なら現在の意味encoderを教師に使う。蒸留による意味保持は未検証。常駐予算と形の意味・表面表現を両方満たした後に、[対象部位と断面半径の学習案](../experiments/scaffold-program-v1/RESEARCH_NEXT.md)を拡張する。

最初の一巡は、無入力の表示、停止、非表示、文章入力、解釈終了後、30分の蓄積を同じ条件で比較する。モデルだけ小さくした測定と、アプリ全体が軽くなった測定を分ける。既存公開版を置き換えず、別版で検証する。
