# 実窓の資源と文字表面の検証計画

2026-10-03。ここに記す測定は未実行の計画。現在のM5/32GBでの短いWKWebView比較と、Metalのoffscreen検証を、一般PCでのウィジェット予算達成へ読み替えない。

## 予算と測定範囲

候補予算は既存の[ウィジェット設計](../widget-first-20261002.md)から引き継ぐ。数値はユーザーの用途に対する設計提案で、OS公式の標準ではない。

| 状態 | 候補目標 | 実際に測る値 |
| --- | --- | --- |
| 約400×400の通常表示 | 15〜20fps、1論理コア換算平均CPU≤5%、全体メモリ目安≤200MiB | 実経過時間、全帰属PIDのCPU時間、同時刻footprint、実frame数、GPU・電力補助値 |
| 一回の描画 | CPU処理時間p95≤3ms | 曲面更新、転送、CPU submitを別に保存。GPU完了時間は別項目 |
| 明示入力・解釈中 | 全工程≤30秒、短時間メモリピーク≤512MiB | 確定入力から文字形成完了まで。モデル初回準備・解釈・compile・吸収を別の区間でも記録 |
| 停止・非表示 | 位置更新0、描画0、アプリ由来CPUはほぼ0 | counters固定、CPUと状態一致。計測の検出限界と空の対照アプリも記録 |
| 長時間表示 | 30分・2時間で継続的な使用量増加がなく保存成功 | 最大容量までの意図した増加と、その後のplateauを分ける |

CPU100%を1論理コアとする。複数コアのPCでOSの表示する全体比率と混ぜない。フレームを落としてCPUが下がった試行は、同じ表示品質の改善として数えない。

メモリは、取得ファイル量、モデル表のbytes、仮想address、プロセスRSS、charged footprint、GPU buffer/atlas、ディスクcacheを別列にする。mmapされた128MiBの表は、全体が常時residentであるとは限らない。関連プロセスの同時刻footprint合計は実装を比較する集計で、共有を完全に除いたシステムRAM差分とは称さない。モデルだけのfile縮小を、アプリ全体RAMの減少率にしない。

200MiBの採否に使う操作上の指標は、OSごとに最終測定前に固定する。Macは既存比較と同じ帰属PIDのcharged footprint合計を主列とし、計上済みか不明なGPU資源は別列に残す。Windowsは利用可能な公式計測の意味を確認してから主列を決め、異なるOSのRSS等を同一の物理RAMとして比較しない。二重計上と未計上の範囲を説明できない場合、全体RAMの目標達成は未確認とする。

CPUだけで低負荷と判断せず、GPU活動、timer、ディスク・ネットワーク、可能なら電力も記録する。AppleのEnergy Impactは複数要因からの指標であり、消費電力Wへ換算しない。定期的な再測定という方針の根拠は公式資料にあるが、本計画の5%/200MiBを同資料から導いたとは言わない。[Apple公式ガイド](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/MonitoringEnergyUsage.html)

## 実機と統制条件

現MacのM5/32GBは工学的な比較環境として残す。主張したい範囲が16GB laptop CPU/iGPUなら、**物理的な16GBノートPC**を少なくとも一台で測る。Windowsも含む一般PCと記す場合は、Windows側の実行物と入力・保存・表示を先に確認し、16GBのx86 laptopでも測る。Macでメモリ上限を設定したものや仮想環境だけを、この実機の代わりにしない。一台ずつの観測なら、その機種での結果と呼ぶ。

OS/build、CPU/GPU、RAM、電源接続、解像度、画素比、画面リフレッシュ、フォント、バックグラウンド作業、温度または取得可能なthermal状態、実行物hashを記録する。モデルの重い試験や別の描画試験を同じ測定窓で並走させない。通常表示・停止・非表示・覆われた状態を別にする。Macのロック中に通常窓の値を作らない。

描画方式の主比較は共通に実装されている球・箱・メビウスの3形で行う。60形の全てをMetalで再現した比較とは書かない。元の文字・色・IDを保存した同じfixtureを、同じ状態と時刻の位相から開始する。描画1,536文字、保存32,000文字までを上限条件とし、少数文字の条件も別に設ける。小窓の実際の外寸は各試行で保存し、400×440の既存結果を400×400の完全一致としない。

## 一回の対照測定

1. 各実行物を別名で保持し、同じ保存fixtureを新しい実験領域へコピーする。最初のshader/font/atlas作成とモデル準備をcold区間として保存する。
2. 主PIDと子PIDの起動前後の差、実行物、process group等で帰属を確かめる。Quit後の消滅まで記録する。無関係なブラウザPIDを足さない。
3. 通常窓を120秒暖機し、300秒の計測窓を取る。0.5秒程度の資源記録と、frames、文字数、paused/visible、Worker有無、model stateを照合する。
4. 各方式・各形を少なくとも5回、順序を交互またはランダム化して測る。先に一回だけ良かった結果を固定の改善率にしない。機種ごとに中央値・範囲・同じ条件での差を示す。
5. 同じ手順で表示中停止、停止を解除して非表示、再表示を測る。再表示時のjump、入力欠落、古い解釈の反映、frame再開を確認する。
6. 状態が途中で変わった窓、telemetryが古い窓、PID帰属不明な窓を無効として理由を保存し、別名で再測定する。数値の悪さを無効理由にしない。元の失敗原票を残す。

停止・非表示のCPUは、固定したframe counterだけで推定しない。CPUの目標を「ほぼ0」とする現段階では、対照アプリとの差と装置の検出限界を報告する。必要なら≤0.1%/1コア等の採用線を開発段階で事前に追加するが、今回の既存値を見て成功の線を決めない。

## 入力とモデルの寿命

明示要求の受理、hold、非対応、入力長上限、取消、次入力による置換を同じ本数で再生する。型どおりの短文だけでなく、32/256/1,024/4,000文字の上限内入力を測る。初回モデル準備、最初の解釈、warm解釈、処理後30/120秒を分け、Worker終了と実メモリの戻りをPID・資源記録で照合する。download時間は全工程の通常値へ混ぜず、取得込みの初回値として併記する。

ambient候補を測る将来の負荷試験では、合成した確定テキストchunkを通常入力速度とburstで供給する。文字追加の待ち時間と、低頻度の意味更新の待ち時間を別に測る。本文受信が続いたことを理由に意味推論を毎回再起動しない。同一内容の再解析回数、queue長、古い返答の破棄数、形変更回数を記録する。OS入力の取得性能や実IMEの性能は、合成再生だけでは検証されない。

## 表面と履歴を保ったか

軽量化前後に、原文の完全一致、Unicode、文字順、旧ID、旧色、保存復元、最大容量、atlas拡張後のtileを検査する。数値では点と接線の有限性、chart seam、shapeの対応、時刻を長く進めたときの差を調べる。IDが同じでも字形が見えない、面が一本の線へ潰れる、裏面が透ける問題は数値検査だけで見つからないため、同じカメラと時刻の画像・実画面も対で比較する。

入力前後・hold・例外・保存失敗の全経路で、本文と旧色が残ることを確認する。文字の保存量を減らす、形を単純な輪に変える、密度を疎らにすることで得た低負荷は、元の表現を保つ改善として数えない。raw画像と数値差を保存し、試遊での可読性と納得は別に尋ねる。

## 長時間の試験

通常実窓で30分、2時間を段階的に測り、必要なら8時間へ延長する。最大履歴・描画容量を事前に満たした静的条件、文字を追加する条件、停止/非表示/復帰を反復する条件を別にする。容量を満たすまでの増加と、同じ容量を保持した後の増加を区別する。最初・中間・終端の同じ状態の窓を比較し、保存成功、frame数、error、timeout、atlas/GPU資源数も照合する。

現段階で数値的なリーク判定線を実証していないため、「絶対に増加0」だけを基準にしない。開発時の候補線として、暖機後の最大容量条件で2時間後の同状態メモリ増分≤20MiBを登録し、区間ごとの傾きも出す。この20MiBは本計画の提案で、allocatorの挙動と保存容量の増加を調べた後、最終試験の前に固定する。

**この文書のスナップショット時点で、Metalの2時間offscreen soakは進行中、完了結果0件である。** 終了後に別の追記版で、実elapsed、frame、エラー、資源とexitを突合する。その結果でも通常のwindow widgetのCPU≤5%・200MiB達成とは扱わない。offscreenはGPU・状態の継続性、実窓は表示と関連プロセスを含む負荷を測る別試験である。
